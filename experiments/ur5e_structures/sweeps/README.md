# Structure sweeps (simulation)

A sweep runs a list of structures once each with fixed controller settings and
keeps the link from every outcome back to its configuration, settings and
video. All results here are Isaac Sim 6.2 simulation, judged by simulator
ground truth; nothing in this folder drives a robot.

## Files

- `<name>.json`: the sweep definition. It holds:
  - the controller commit;
  - the sweep environment (applied to every run);
  - per run: label, config, environment overrides, run id (the run folder under `outputs/ur5e_assembly/`), video and committed media.
- `<name>.summary.json` and `<name>.summary.md` are generated by
  `summarize_sweep.py` from the definition and the raw outputs. Do not edit them.
- The raw outputs are not in git, being large and machine-specific: run folders, recordings
  (`outputs/ur5e_lego/*.jsonl`), utilization CSVs and full-resolution videos
  (`.cache/videos/`). The summaries name each of them.

## Run and summarize

```bash
# Runs every entry without a run id and writes the id back into the definition.
OMNI_KIT_ACCEPT_EULA=YES python3 -m experiments.ur5e_structures.run_sweep \
  experiments/ur5e_structures/sweeps/<name>.json [--capture]
python3 -m experiments.ur5e_structures.summarize_sweep \
  experiments/ur5e_structures/sweeps/<name>.json
```

To reproduce a committed sweep, check out the controller commit it names and
run it into a fresh copy, then summarize the copy and compare it with the
committed summary:

```bash
OMNI_KIT_ACCEPT_EULA=YES python3 -m experiments.ur5e_structures.run_sweep \
  experiments/ur5e_structures/sweeps/2026-11-08-showcase-sweep.json \
  --rerun experiments/ur5e_structures/sweeps/my-rerun.json --capture
python3 -m experiments.ur5e_structures.summarize_sweep \
  experiments/ur5e_structures/sweeps/my-rerun.json
```

On the machine that produced these sweeps, repeated runs matched exactly:
- same outcomes;
- same joint breaks;
- same simulator step of every logged joint event.

On other GPUs or drivers, expect the same outcomes but not necessarily
bit-identical steps. The failure and capture sweeps were first run with an
equivalent shell loop; their definitions were written from that loop's run
lists and result tables.

## What a summary distinguishes

A failed run can mean very different things. The summary keeps the following apart:

1. **What stopped the controller** (`failure_class`). It is the controller's
   first failure, not a physics verdict:
   - `joint_lost`: a placed brick's joint to its support is gone at the check
     after the retreat.
   - `not_seated`: the press ended without a connection.
   - `lost_from_grasp`: the brick was more than 2 cm from the tool when the press
     failed, so it was dropped earlier.
   - `no_release_clearance`: the controller refused to open the gripper next to a
     neighbour.
   - `gripper_contact_abort`: the contact monitor stopped the run.
   - `grasp`, `misplaced`, `other`.
2. **Contact logging versus fail-on-contact.**
   - `ASSEMBLY_GRIPPER_CONTACT=fail` (the default) stops a run at the first gripper
     contact with another brick, which gives `gripper_contact_abort`.
   - `log` records the contact (`gripper_contacts`) and lets the run go on.
   - Every sweep here used `log`, so contacts never stopped a run in them.
   - A contact abort is a safety-policy outcome, not a structure failure.
3. **Breakage settings** (`breakage_enabled`, `breakage_settings`).
   - These come from the recording, i.e. what the simulator applied.
   - With breakage off, no joint can break and only the controller's own checks
     can fail a run.
4. **Numerical trouble versus modeled overload**, per joint break:
   - `overload seen`: utilization of at least 1 was sampled in the 0.5 s before
     the break. The breakage model judged the joint overloaded.
   - `sudden`: no sampled overload. Only the breaking step, which is never
     sampled, reached 1.
   - `after solver warnings`: the breakage solver failed to converge, or reported
     high slack, since the previous joint event. A non-converged step changes no
     utilization and breaks nothing. The step that breaks the joint is the next
     converged one, so the break follows numerically suspect solves.
   - `rejoined`: BrickSim re-formed the same joint within 1 s (from the
     recording for planned joints, else from the console). This is a transient
     break the structure survives in ground truth, and the controller never sees
     it.
   - A utilization of `exhausted` is BrickSim's 1e6 sentinel for no remaining
     capacity, not a load value.

## Known telemetry limits

These are findings from the failure, capture and showcase sweeps (38 runs). Each
one bounds what a summary can claim:

- **The breaking solve is not sampled.** Utilization is read after each physics
  step, and by then the broken joint is gone. A `sudden` break is therefore
  not explained by the telemetry. Logging the breaking solve's utilization in
  BrickSim would close this gap.
- **The console log can lose BrickSim events.** Kit flushes its log
  asynchronously and the run ends with `os._exit`, so events after the last
  flush are lost. Both human runs lost every one.
  - 13 of the 38 runs are affected, all completed runs
    (`event_log_complete: false`). Their break and warning counts are lower
    bounds.
  - For each brick's joint to its planned support, the recording samples the
    connection every step. The summary uses it to decide whether a break
    re-formed, to detect a log that missed events, and to add the breaks it
    missed (cause `not in console log`). For example, the dog's last joint
    broke and re-formed 16 ms later, and only the recording shows it.
    Breaks of other joints in such a run may still be missing.
  - Fix for future runs: write joint events into the recording, not only the
    log.
- **Some controller settings are not recorded in the run itself.**
  - Breakage and the required press force are in every recording sample.
  - The gripper-contact mode, press depth and timing come from the sweep
    definition or the controller defaults (each setting's `source` says
    which).
  - Later runs also print `controller settings {...}` with the tunable
    values they used, and the summary reads it.
- **One run per setting.** The 6.2 runs are deterministic. Paired runs in the
  failure and capture sweeps agree in:
  - outcome;
  - simulated time, except where the capture's hold differs;
  - contacts;
  - solver warnings;
  - joint breaks;
  - the BrickSim step of every joint event present in both logs.

  The pairs are dog, human, cantilever, and column against the 1 N press run.

  Sensitivity to initial conditions is not measured. The seed variants of the
  dog are the only perturbation runs.
